## 1. Executive Summary

A comprehensive audit of the notification subsystem was performed to address two primary defects:
1. **Duplicate Arrival Notifications:** When an arrival occurred, `dispatcher.ts` published an event with ID `arrival_${Booking_ID}`, while `StaffWebsite.tsx` polling published an event with ID `arrival_poll_${Booking_ID}`. Because `notificationHub.hasSeen` tracked distinct event keys, two stacked popups appeared for every arrival.
2. **Unauthorized Notification Leaks to Admin Portal:** In `UniversalNotificationCenter.tsx`, the `isEventRelevantForRole` matrix permitted the `Admin` role to receive operational alerts (`ARRIVAL_REGISTERED`, `ARRIVAL_VERIFIED`, `TABLE_ALLOCATED`, `CUSTOMER_SEATED`, `NEW_ORDER`, `ORDER_STATUS_CHANGED`). This caused the Admin Website to display host-desk arrival verification popups that belong strictly to floor Staff.

Both issues have been eliminated through unified deterministic event identifiers and a strictly enforced role-permission routing matrix.

### 2.2 Implementation in `UniversalNotificationCenter.tsx`

```typescript
function isEventRelevantForRole(
  event: RestaurantNotificationEvent,
  role: string
): boolean {
  switch (event.type) {
    case 'NEW_RESERVATION':
      return role === 'Staff' || role === 'Admin';
    case 'ARRIVAL_REGISTERED':
      // Arrival verification belongs strictly to host desk / floor Staff
      return role === 'Staff';
    case 'ARRIVAL_VERIFIED':
    case 'TABLE_ALLOCATED':
    case 'CUSTOMER_SEATED':
      // Table seating updates belong to Customer and floor Staff
      return role === 'Customer' || role === 'Staff' || role === 'Guest';
    case 'NEW_ORDER':
      // Kitchen order tickets belong strictly to Kitchen and floor Staff
      return role === 'Kitchen' || role === 'Staff';
    case 'ORDER_STATUS_CHANGED':
      return role === 'Customer' || role === 'Kitchen' || role === 'Staff' || role === 'Guest';
    case 'BILL_GENERATED':
      return role === 'Customer' || role === 'Staff' || role === 'Guest';
    case 'PAYMENT_VERIFIED':
      // Payments require visibility for Customer, Staff and Admin
      return role === 'Customer' || role === 'Staff' || role === 'Admin';
    default:
      return true;
  }
}
```

## 3. Duplicate Notification Elimination & Key Unification

### 3.1 Root Cause of Duplicate Popups
Prior to this fix, the system maintained discordant ID naming schemes between direct user actions and background polling loops:

```
[Direct Action in dispatcher.ts]  ──> ID: arrival_BK-20261112-9006  ──> notificationHub (Saved)
[Polling in StaffWebsite.tsx]     ──> ID: arrival_poll_BK-20261112-9006 ──> notificationHub (Treated as New!)
```

This produced two simultaneous notifications:
1. One with direct actor metadata: `"Customer Guest (BK-20261112-9006)"`
2. One with database record metadata: `"Guest Heran (BK-20261112-9006)"`

### 3.2 Unified Deterministic Identifier Standard
All publishing sites now adhere to unified, deterministic keys:

| Operational Event | Former Discordant Keys | Unified Deterministic Standard |
| :--- | :--- | :--- |
| **Customer Arrival** | `arrival_${id}` vs `arrival_poll_${id}` | `arrival_${Booking_ID}` |
| **New Reservation** | `res_${id}` vs `res_poll_${id}` | `res_${Booking_ID}` |
| **Kitchen Order Ticket**| `order_${id}` vs `kitchen_poll_${id}` | `order_${Order_ID}` |
| **Bill Generation** | `cust_bill_${id}` vs `bill_${bId}_${id}` | `bill_${Booking_ID}_${Bill_ID}` |
| **Order Status Update** | `kitchen_${id}_${status}` vs `cust_ord_${id}_${status}` | `kitchen_${Order_ID}_${Order_Status}` |
